担当者が商品を探し、見積を依頼し、回答を受け取り、顧客の申込を送信する。各段階で操作は発生しますが、クリックの増加が証券発行の増加を意味するとは限りません。

発行時保険料が80万人民元から60万人民元へ減ったら、流入、価格、申込プロセスのどこから調べるでしょうか。見積依頼から証券発行までを追い、仮の数値で調べてみます。対象はプラットフォームの利用と申込で、保険会社全体の経営や担当者の業績評価は含みません。

## 1. まず、何を改善したいかを決める

ここでの目的は、**失敗や不要な待ち時間を減らし、より多くの見積依頼を証券発行まで進めること**です。 証券数と発行時保険料で成果を見て、転換率、所要時間、失敗率で問題の場所を調べます。

困っていることが違えば、先に見る数も変わります。「送信が何度も失敗する」なら送信成功率とエラー理由、「見積を待つ時間が長い」なら待ち時間を調べます。全指標を同じ重さで並べると、優先順位がかえって見えなくなります。

ダッシュボードでは、これらを分けて表示します。

| 層 | 答えたい問い | 主な指標 |
| --- | --- | --- |
| 業務の成果 | 有効な業務が最終的にどれだけ完了したか | 発行済み証券数、総保険料、一件当たり保険料 |
| プロセスの効率 | どの段階で進み、どこで止まるか | 各段階の転換率、待ち時間、完了までの時間 |
| 利用と品質 | 誰が使い、操作を円滑に完了できるか | 機能利用者数、アクティブ率・継続率、失敗率、エラー理由 |

チャネル、商品、利用環境、証券発行の方式、利用者区分は、指標を分解するための切り口です。例えば「モバイルWeb」は利用環境の一つの区分であり、「モバイルWebでの申込送信成功率」が具体的な指標になります。

最初に証券数と発行時保険料を置き、そこからプロセスを調べます。保険料が減った場合は、証券数が減ったのか、一件当たり保険料が下がったのかを分けます。証券数が減っていれば、どの段階で業務が止まったかを優先して確認します。

## 2. 一件の保険業務は、どのように完了するか

いったんページ名から離れ、一件の業務が始まりから終わりまでに何を経験するかを見ます。

<picture>
  <source media="(max-width: 640px)" srcset="/images/blog/insurance-platform-metrics/business-flow.ja.mobile.svg" />
  <img src="/images/blog/insurance-platform-metrics/business-flow.ja.svg" alt="保険業務の分析フロー：商品検索・選択、見積依頼の送信、利用可能な見積の取得、申込手続きへの移行、申込送信、別途定義を確認する証券発行。" loading="lazy" />
</picture>

これは分析のための基本フローです。実際のサービスでは、一部の段階を省略したり、担当者とのやり取り、資料の追加、支払いなどが入ったりします。最終的な「証券発行成功」をどのシステム上の状態で判定するかは、実際の業務に確認する必要があります。画面名だけで判断してはいけません。

### 操作が発生しても、業務が完了したとは限らない

同じ段階でも、少なくとも三つの状態を区別できます。

| 状態 | 例 | 答えられる問い |
| --- | --- | --- |
| 操作の意図 | 「保険を申し込む」をクリック | 続けようとしたか |
| 操作の完了 | バックエンドが申込送信の成功を確認 | 送信が実際に完了したか |
| 業務の成果 | 合意した証券発行成功の状態に到達 | 有効な業務につながったか |

これらは置き換えられません。利用者が何度もクリックすることも、クリック後に入力チェックで失敗することもあります。送信が成功しても、その後の処理が続いている場合があります。

クリックは操作の分析、送信結果は操作完了率の分析、最終的な業務状態は成果の集計に使います。証券数や保険料は、対応する業務記録から取得します。

### 画面の経路が違っても、比較する段階をそろえる

PC向けWebとモバイルWeb、通常の見積依頼と事前の取り決めに基づく発行経路、新規と継続では、画面や入口が異なることがあります。クリック経路ごとに独立したファネルを作ると、比較しにくいレポートが増えてしまいます。

まず共通する業務の段階を定義し、具体的な経路を対応付けます。業務区分と入口も分けます。新規・継続は業務区分ですが、よく使う商品、コピー、各ボタンは入口や派生経路になり得ます。すべてを排他的な新規業務の種類として扱うべきではありません。

| 実際の経路 | 分析時の扱い |
| --- | --- |
| 通常の商品見積依頼・よく使う商品からの入口 | 入口の違いを残し、見積依頼の送信成功を共通の段階として確認 |
| 見積依頼のコピー | 元の業務と新しいフローを区別。同じフロー内の変更・再試行は別に記録 |
| 事前の取り決めに基づく証券発行 | 経路の識別情報を残し、実際に通る段階を確認 |
| 新規・継続 | 業務区分を分け、それぞれの段階間の転換を分析 |
| 手動見積・自動見積 | 見積方式を分け、成功率と待ち時間を比較 |
| 一括申込 | バッチと子案件を関連付け、両者の完了を別々に集計 |
| 暫定契約から正式契約への移行 | 元の記録と正式証券を関連付け、重複計上を防ぐ規則を定義 |

この対応付けは、「どの業務区分が、同じ段階で異なる動きをしているか」を確認するためのものです。

ある経路が特定の段階を通らないなら、その段階を含むファネルをそのまま当てはめません。両方が通る段階で比較するか、経路を分けて表示します。

## 3. 各段階で、一つずつ問いに答える

一件の申込を追いながら、各段階の操作と、その結果を分けて見ていきます。

### 1. 商品検索：必要な入口を見つけられるか

- **閲覧とクリック**：ページ閲覧数とボタンクリック数を分けて数えます。
- **利用者数**：入口を使った異なるアカウントの数です。一つのアカウントが十回押しても、利用者は一人です。
- **機能利用率**：権限と利用機会のあるアクティブ利用者のうち、実際に使った割合です。

クリックが少なければ入口の見つけやすさを確認します。クリックが多いのに見積依頼へ進まなければ、検索結果、画面の案内、次の操作を調べます。

<details class="insurance-metric-note">
  <summary>計算の詳細：CTR、機能利用率、検索、共有</summary>

- **ページ閲覧数（PV）とボタンクリック数**：別々に集計します。クリックは有効なイベントをevent_idで重複排除し、再試行で発生した新たな操作は別イベントとして記録できます。
- **利用者数（UV）**：操作した利用者の重複排除数です。アカウントと訪問者識別子など、どの単位を使うかを明示します。
- **機能利用率**：利用権限と利用機会のあるアクティブアカウントのうち、その機能を使った割合です。
- **表示インスタンス単位のボタンCTR（P04）**：一回以上クリックされたボタン表示数を、有効なボタン表示数で割ります。impression_idで表示とクリックを関連付け、実際に見える表示を数えます。同じ表示への複数回クリックは一つとして数えます。

分母が異なります。機能利用率は対象アクティブアカウントへの広がりを、CTRは有効な表示後の反応を表します。

人単位で見るなら、同じ表示利用者集団のクリック人数を表示人数で割る「利用者クリック率」を別に定義できます。表示単位のCTRと集計単位が違うため、名前も分けます。信頼できる表示記録がなければ、どちらも推定しません。

例えば、40人が100回の有効なボタン表示を生み、そのうち20回の表示を12人がクリックし、クリックイベントは35回発生したとします。表示単位CTRは20 ÷ 100 = 20%、利用者クリック率は12 ÷ 40 = 30%です。35回は操作量を表し、どちらの分子にもそのまま使えません。数値は集計単位の違いを説明するための例です。

検索有効結果率P06は、少なくとも一件の有効な結果を返した成功検索リクエスト数を、全有効検索リクエスト数で割ります。タイムアウトとAPI失敗も分母に残し、理由を別に示します。入口の利用と有効な結果の取得は、別の問いです。

同じ検索ボタンが複数の画面にある場合は、画面や位置も記録します。まとめるだけでは、利用者がどこで機能を見つけたかが分かりません。

共有回数と共有人数も記録できます。成功の応答がある場合は共有成功、ない場合は共有開始と呼びます。開始だけで相手への到達を推測してはいけません。その後の見積や申込を見るには、業務を追跡できる必要があります。

</details>

### 2. 見積依頼：必要な情報を送信できるか

「見積を依頼する」のクリックは、有効な見積依頼の送信と同じではありません。入力画面への到達、入力開始、送信成功について、それぞれ何件の業務フローが到達したかを追います。

ここでは三つの指標が役立ちます。

- **見積依頼の送信成功フロー数**：送信が完了した業務フローの重複排除数。
- **見積依頼の入力完了率**：入力段階に入った同じ集団のうち、所定の観測期間内に送信を完了した割合。
- **見積依頼の入力所要時間**：入力段階への到達から、最初の送信成功までの時間。

観測期間は、次の行動が起きるまで待つ時間です。例えば入力開始から七日以内の送信を見るなら、どの業務にも七日間の機会を与えます。同じ起点で選んだ集団を「コホート」と呼び、期間をすべて観測できた集団だけで比較します。七日は説明用の例で、実際の期間は業務に合わせます。

入力画面への到達数が変わらず、完了率だけが下がった場合は、必須項目、入力チェック、資料アップロード、APIの応答を確認します。入口への流入を増やすだけでは、解決しない可能性があります。

### 3. 見積提示：送信した依頼に適時に回答が届くか

**見積取得率**は、有効な見積依頼の同じ集団のうち、所定の期間内に少なくとも一つの利用可能な見積を取得したフローの割合、と定義できます。

一件の依頼に複数の見積版ができたり、複数の提示者が関わったりすることがあります。業務ファネルでは、見積を取得したかどうかをフロー単位で数えます。作業量を調べる場合は、見積の件数を別に数えます。集計する対象が異なります。

どれくらい待つかも確認します。P50は待ち時間の中央値、P90は遅い側の状況を見る値です。例えば、見積取得済み業務の待ち時間P90が30分なら、およそ九割は30分以内に見積を得ています。平均だけでは、特に遅い一部の業務を見落とすことがあります。

見積を取得済みのフローだけで待ち時間を計算する場合は、見積待ちのフロー数と現在までの待ち時間も示します。まだ待っている遅い業務を除くと、実態より速く見えるためです。

<details class="insurance-metric-note">
  <summary>詳しく比較する：手動見積と自動見積</summary>

手動見積と自動見積は分けて表示します。見積成功率F05は、観測が完了した同じ見積処理集団で、W内に有効な見積を得た重複排除依頼数を、見積処理に提出した依頼数で割ります。扱う業務の複雑さが異なる可能性があるため、商品、チャネル、資料の充足度と合わせて解釈します。

初回と最終の見積方式、手動への引継ぎ、自動処理からの切替も保持します。最終方式での分類は処理結果を説明します。自動見積の能力を評価するなら、最初に自動処理へ入った同じ集団も追います。失敗後に手動へ移った案件を自動群から外すと、結果が偏るためです。

その集団について、自動処理内での成功、手動への引継ぎ、最終的な見積取得を分けて見ます。手動に引き継いで見積を取得できても、自動処理が成功したことにはなりません。

</details>


### 4. 申込への移行と送信：見積後に業務が進むか

見積後は、次の二段階を分けて見ます。

- **申込手続きに進んだか。** 保険料、保障内容、顧客の判断、担当者のフォローなどが影響します。
- **手続きに入った後、送信できたか。** 情報入力や送信の問題はこちらで調べます。

後者は、同じ業務集団で計算します。

> **申込送信成功率 = 同じ申込開始集団のうち、所定の期間内に送信が成功したフロー数 ÷ その集団の全フロー数。**

分子は、分母に含まれる同じフローから数えます。「今日の送信成功数」を「今日の申込手続き開始数」で割るだけでは、対象が一致しないことがあります。今日送信した業務は、昨日手続きを始めたかもしれません。

日次レポートでは、その日に各段階で何件起きたかを見ます。転換率では同じ業務を追跡するため、日次の件数をそのまま割ることはできません。

<details class="insurance-metric-note">
  <summary>計算の詳細：同じ業務集団、観測期間、全体転換率</summary>

申込送信成功件数B09は、バックエンドが受け付けたapplication_idを重複排除し、クリック数は使いません。段階未転換率F03は、同じ観測済み集団の1 − F01です。待ち、拒否、期間外の完了も含まれ得るため、すべて自発的な離脱とは限りません。

見積依頼から発行までの転換率F02も使えます。観測が完了した同じ見積依頼開始集団のうち、期間W内に一件以上発行成功した依頼数を、その集団の全依頼数で割ります。見積未取得や後続の失敗も分母に含め、一依頼から複数証券が発行されても成功依頼は一件です。

観測の起点も明示します。全体の転換は見積依頼開始から、単一段階の完了率はその段階への到達から測れます。同じファネル内で、説明なく起点を混ぜてはいけません。

</details>


### 5. 最終的な成果：有効な業務は何件完了したか

まず二つの数を見ます。発行に成功した証券は何件か、その同じ証券の発行時保険料はいくらか。バックエンドで確認した成果を使い、クリックで証券数を代用しません。

証券の集合と金額の条件が一致していれば、次の分解が使えます。

> **総保険料 = 証券数 × 一件当たり保険料。**

総保険料が減ったら、まず証券数、一件当たり保険料、または両方が変わったかを確認します。

- 証券数の減少：業務の流入元、各段階の転換、最終的な完了状況を確認。
- 一件当たり保険料の減少：商品構成、保険金額、業務区分、価格などを確認。

<details class="insurance-metric-note">
  <summary>金額の詳細：初回発行、実入金、契約者当たり保険料</summary>

B01は、期間内にバックエンドが初めて発行成功を確認したpolicy_idの重複排除数です。B02は、その証券集合の初回発行時の保険料スナップショットを通貨別に合計します。後の解約、契約変更、返金、無効化の取消は別に追い、過去の発行時金額を上書きしません。

初回発行の規模と、ある時点で有効な契約の規模は別指標です。発行時保険料は、実入金、既経過保険料、正味保険料とも異なります。実入金B08は成功した入金取引を重複排除し、入金日時で集計し、返金は別に示します。発行日と入金日は一致しない場合があります。

契約者当たり保険料B05は、B02を同じ発行証券集合のpolicyholder_idの重複排除数で割ります。契約者には個人と法人があるため、契約主体当たりの保険料と理解できます。操作アカウントや被保険者を分母に代用せず、別の平均指標には別の名前を付けます。

保険金額の合計や一件当たり保険金額も補助指標になります。ただし、異なる保険種目を比較するときは、金額の意味が比較可能かを確認します。数値を足せることと、業務上比較できることは同じではありません。

</details>


## 4. 誰が使い、どこで困っているかを調べる

変化が特定の利用者、商品、入口に集中している場合もあります。全体に起きた問題と決めつけず、分けて見ます。

### 操作する利用者と保険契約者は別の役割

操作する利用者は、営業担当者、提携チャネルの担当者、その他のアカウントである場合があります。一方、保険契約者と被保険者は保険業務上の役割です。具体的な関係は、実際のプラットフォームで確認します。

これらを混ぜると、アクティブ率、継続率、一人当たり保険料の意味が曖昧になります。

操作アカウントでは、新規登録U01と、一日・一週・一か月に一回以上、有効な業務操作をしたアカウントの重複排除数、DAU・WAU・MAU（U02）を見ます。検索、見積依頼開始、申込送信、サービス手続きなどは候補です。業務目標に合わせて行動リストを確定し、版を管理します。表示だけでは業務アクティブに数えず、暦週・暦月の境界とタイムゾーンを統一します。

新規登録と初回の業務利用は別に命名します。テスト、機械、内部運用アカウントは明確な規則で除外します。営業担当者などが実際の利用者なら、従業員という理由だけで除外しません。

特定日継続率U03は登録日別の集団を使います。その集団のうち、N日目に有効行動をした重複排除人数を登録人数で割り、Nは1・7・30などとします。D7は七日目当日の再利用であり、最初の七日間のどこかで戻ったことではありません。観測期間が完了した集団のみ比較します。これは利用者の継続率で、契約継続率ではありません。

初回の主要行動を起点にした週次継続率は、登録日継続率とは別の活性化指標として設けられます。

定着度U04は、その月の平均DAUを同月のMAUで割ります。一日のDAUを月全体の代表値にしません。保険業務の頻度は役割や業務周期と合わせて解釈します。

### 属性は差異の説明に使い、好みは表示条件と合わせて見る

保険契約者、被保険者、保険種目、商品の属性を使って、業務を分けて分析できます。「変化はどの種類の業務に集中しているか」を確認するためです。

行動から好みを探ることもできますが、クリックが多いだけでは好みが強いとは限りません。表示回数が多い、上の位置にある、初期状態で選ばれている、といった可能性があります。クリックの差は、表示や入口の条件と合わせて確認します。

### 失敗回数に加えて、失敗率と復旧を確認する

失敗の増加は、問題の増加か業務量の増加かもしれません。まずリクエスト単位とフロー単位を区別します。

「リクエスト」は、フォーム送信のようにシステムへ送る一回の操作です。同じ申込を何度も送る場合があるため、失敗回数と影響を受けた業務件数を分けて見ます。

失敗回数E01はrequest_idで重複排除します。この例では、明確な失敗と確定したタイムアウトを両方とも失敗の分子に含めます。失敗率E02 =（明確な失敗数 + 確定タイムアウト数）÷ 終端状態に達した有効リクエスト数です。完了日時の範囲をそろえ、レポート締切時点で各リクエストを一つの終端状態として数えます。処理中は別表示し、エラー理由とタイムアウト理由を保持します。

例えば、終端状態100件の内訳が成功90件、明確な失敗8件、確定タイムアウト2件なら、失敗率は（8 + 2）÷ 100 = 10%です。別に処理中が5件あっても、この分母には含めません。実システムでタイムアウトを別定義にする場合は、別の名前と率を併記し、この記事の条件と混ぜません。

影響フロー率は、一度以上失敗した重複排除フロー数を、同じ集団でその操作を試みたフロー数で割ります。業務への影響範囲であり、リクエスト失敗率とは別です。

再試行も分けて記録します。一件が五回失敗して最後に成功した場合と、五件が一回ずつ失敗してすべて離脱した場合では、体験が異なります。

レポートには次を並べて表示できます。

- 失敗したリクエストの回数：未成功の発生量。入力チェック、権限、システム障害などの理由を分けて確認。
- 一度以上失敗したフローの重複排除数：影響を受けた業務の範囲。
- 失敗したフローのうち、観測期間内に復旧して成功した割合：問題を解消できたか。

エラー理由は、入力チェック、認証、権限、APIタイムアウトなどに分類できますが、実際の記録に基づいて分類します。登録・ログイン、本人確認、オンラインサービス手続きには、それぞれのフローを作り、必要に応じて申込の主フローと関連付けます。

オンライン手続きの完了率E04は、観測期間が完了した同じサービス申請集団で計算します。所要時間E05は完了済みのP50・P90と、未完了件数・待ち時間を併記します。同じ種類のサービスで比較します。

保険金請求・支払は任意の独立した業務サイクルです。C01は終結済みで累計支払額が正の案件数を終結日で集計し、C02は実際の支払成功取引を支払日で集計します。C03はC01案件の保険種目構成です。終結と支払は異なる期間になるため、C02はC01案件の累計金額を単純合計した値ではありません。データを接続できた段階で導入し、申込ファネルには混ぜません。

## 5. 同じ指標でも答えが変わるのはなぜか

同じ「送信成功率」でも、クリック数で割る人と、申込手続きに入った業務数で割る人がいれば、値は一致しません。後から差を調べるより、先に計算の条件をまとめておく方が早く確認できます。申込送信成功率なら、次のように定義します。

| 項目 | 明示する内容 |
| --- | --- |
| 業務上の問い | 申込手続きに入った後、円滑に送信できるか |
| 集計単位 | クリック数や人数ではなく、重複排除した業務フロー |
| 分母 | 定めた開始日時の範囲で、初めて申込手続きに入ったフロー |
| 分子 | 分母のフローのうち、観測期間内にバックエンドで送信成功を確認したもの |
| 重複排除・版 | 同じフローの再試行の扱いと、新たに開始した業務の識別 |
| 時間条件 | タイムゾーンを統一し、段階の開始日時と送信成功日時を保持 |
| データ元 | 業務状態またはサーバー側の成功イベント。画面上の計測は行動を補足 |
| 分解の切り口 | 商品、チャネル、利用環境、証券発行の方式、見積方式など |
| 未完了の業務 | 処理待ち、明確な失敗、観測期間内の未完了を区別 |

### ファネルを計算する前に、記録をつなぐ

段階を横断する分析用のフロー識別子を持ち、見積依頼、見積、申込、証券との対応関係を管理できると理想的です。これはデータ設計の提案であり、既存システムにすでにその項目があるという意味ではありません。

利用者アカウントだけでは、同時に進める複数の業務を区別できません。画面の時刻だけでも、変更、再試行、端末をまたぐ操作を確実につなぐことは困難です。

一件の見積依頼から複数の証券が発行される場合は、成功フロー数と証券数を別に集計します。証券数を見積依頼フロー数で割って、通常のフロー転換率と呼ぶべきではありません。

IDの重複・欠落、状態の時間順序、関連付けの欠落、端末間の重複、金額異常、遅延イベントも確認します。分母ゼロはN/A、未知や未取得は欠損として表示します。データがないことはゼロとは異なります。

### 各集団に十分な観測時間を与える

ある段階に入ってから七日以内の完了を観測するとします。開始から一日しか経っていない業務には、十分な観測時間がありません。七日間観測済みの集団と直接比較すると、新しい集団の完了率を過小評価します。

「観測期間が完了した集団」と「まだ観測中の集団」を分けて示します。七日は説明用の例であり、実際の期間は業務の進み方に応じて決めます。期間を超えて完了した業務も、別に追跡できます。

次の段階に進んでいないからといって、失敗したとは限りません。処理待ち、自発的な離脱、技術的な失敗、期限内の未完了は、できるだけ分けて記録します。

## 6. 保険料が25%減った例で考える

冒頭の問いに戻ります。発行時保険料が80万人民元から60万人民元へ減ったら、どこから調べるでしょうか。

**この節の数値と調査の経緯は仮のものです。** 二つの集団は、次の条件で比較します。

- 見積依頼の送信が成功した1,000件ずつの二つの集団を比較します。各フローを送信成功から同じW日間追跡し、全件で観測期間が終了しています。
- 各段階は同じフロー内で順番に進みます。一つの段階では一フローを一回だけ数え、発行できる証券は一フローにつき最大一件とします。
- 証券数と保険料は、その二つの集団からW日以内に生じた成果です。人民元と同じ初回発行の条件を使います。発行日別に集計した、プラットフォーム全体の月報とは区別します。

| 段階・成果 | 前の集団 | 現在の集団 |
| --- | ---: | ---: |
| 見積依頼の送信成功フロー数 | 1,000 | 1,000 |
| 利用可能な見積を取得したフロー数 | 800 | 800 |
| 申込手続きに入ったフロー数 | 560 | 560 |
| 申込送信が成功したフロー数 | 448 | 336 |
| 発行成功の証券数 | 400 | 300 |
| 一件当たり保険料 | 2,000人民元 | 2,000人民元 |
| 総保険料 | 800,000人民元 | 600,000人民元 |

これは見積依頼の送信成功後の部分ファネルです。開始したが送信していない依頼を含まないため、先ほどの全体転換率F02とは呼べません。

### 手順1：比較できる成果かを確認する

減少を説明する前に、集計条件、観測期間、金額の扱いが一致するかを確認します。データの遅延、イベントの欠落、業務状態の変更も、報告される数値に影響します。

定義が変わった場合は、その影響を先に確認します。数値の差をそのまま業務の悪化と解釈しないためです。

### 手順2：総保険料を証券数と一件当たり保険料に分ける

一件当たり保険料は2,000人民元で変わらず、証券数が400件から300件に減っています。そのため総保険料は80万人民元から60万人民元へ減り、減少率は25%です。

平均は変わっていません。次は、減った100件がどの段階で止まったかを調べます。

### 手順3：変化が最も明確な段階を見つける

主表の隣り合う段階を割ると、次のようになります。各行とも、見積依頼の送信成功から同じW日間で集計しています。

| 段階 | 前の集団 | 現在の集団 |
| --- | ---: | ---: |
| 見積依頼送信 → 見積取得 | 800 ÷ 1,000 = 80% | 800 ÷ 1,000 = 80% |
| 見積取得 → 申込手続き開始 | 560 ÷ 800 = 70% | 560 ÷ 800 = 70% |
| 申込手続き開始 → 送信成功 | 448 ÷ 560 = 80% | 336 ÷ 560 = 60% |
| 送信成功 → 証券発行 | 400 ÷ 448 ≈ 89.3% | 300 ÷ 336 ≈ 89.3% |

変化したのは「申込手続き開始 → 送信成功」です。80%から60%へ、**20ポイント**下がっています。以前の80%を維持した場合の448件に対し、実際は336件で、差は112件です。送信後の発行割合は変わらず、最終的な証券数は400件から300件に減っています。

これは表の数値の差を説明するもので、送信システムの障害を証明するものではありません。顧客の保留、入力途中の離脱、入力チェックの失敗などでも、ここで止まります。

### 手順4：具体的な業務区分に分解する

まず、申込手続きに入った時点の利用環境で分けます。後で端末を変えても、同じフローは一つの区分にだけ数えます。560件の内訳が次のとおりだったとします。

| 申込開始時の利用環境 | 前の集団：送信成功数 / 開始数 | 現在の集団：送信成功数 / 開始数 |
| --- | ---: | ---: |
| PC向けWeb | 224 / 280 = 80% | 224 / 280 = 80% |
| モバイルWeb | 224 / 280 = 80% | 112 / 280 = 40% |
| 合計 | 448 / 560 = 80% | 336 / 560 = 60% |

PC側は変わらず、モバイル側で112件減っています。主表の差と一致します。開始数と両者の構成比も変わっていないため、この例の減少はモバイルの割合が増えたためではありません。まずモバイルの送信を調べ、商品、チャネル、フォームの版でさらに絞ります。

実際の分析では、区分内の転換率と区分の構成比を両方確認します。各区分の転換率が変わらなくても、転換率の低い区分の割合が増えれば、全体は下がります。

### 手順5：仮説を立て、検証を計画する

仮の調査を続けます。モバイルのある版のフォームで入力チェックの失敗が増え、失敗後に再送信が成功した割合も下がっていたとします。フォームやチェック規則を疑う理由にはなりますが、減少のすべてを説明できたわけではありません。

1. **対象業務を照合する。** エラーログをフローIDにつなぎ、その集団の送信未完了業務でエラーが起きているかを確認します。同じ業務が何度再試行しても、影響業務は一件です。
2. **変更を調べる。** フォームの公開時刻、エラーコード、項目の規則を照合し、画面とサーバーのチェック不一致などを再現できるか確かめます。エラーのない未完了業務は、顧客の保留、離脱、資料待ちなどを別に調べます。
3. **修正後を確認する。** 問題を確認して修正したら、同種の業務で送信成功率、所要時間、失敗後の復旧率、その後の証券発行を比べます。各集団は同じ観測期間を満たす必要があります。無効化、解約、返金も追い、送信件数だけを増やして後続の品質を落とさないようにします。

条件が合えば、対象業務を無作為に分け、修正版と従来版を比較できます。ただし、実験のために緊急の修正を遅らせません。修正前後だけの比較では、チャネルや商品の構成、季節変化も確認し、回復のすべてを修正の効果とはしません。件数も併記し、数件の変動を確かな改善と取り違えないようにします。

## 7. 主要指標から始め、少しずつ広げる

最初のダッシュボードでは、証券数、保険料、主な転換率、失敗率を正しく計算します。他の指標は後から追加できます。

- **P0：証券発行と申込の指標を整える。** 発行・送信状態と業務IDの関係を確認し、B01/B02/B09、F01/F02、E01/E02を整備します。件数、金額、転換、失敗を正しく計算することが先です。
- **P1：どの区分に差があるか調べる。** 利用者、機能、所要時間、属性を加え、利用環境・商品・チャネル・役割の差を説明します。
- **P2：保険金分析や他のサービスを追加する。** 保険金分析、任意サービス、細かな切り口を、それぞれの独立した業務サイクルとして接続します。

公開前に、業務定義を確認する人、計算規則を維持する人、データの更新頻度を決めます。信頼できる基準値を得てから目標値を設定し、期間W、タイムゾーン、有効行動は実際の業務に合わせます。

## 次の分析にも、この手順を使う

自動車販売なら「見込み客の登録 → 試乗 → 見積 → 契約 → 納車」、商品購入なら「閲覧 → カート追加 → 注文 → 支払 → 注文の履行」から描き始められます。これは出発点であり、実際の商品に合わせた確認が必要です。カートを通らず直接注文する経路などもあり得ます。

成功状態、数える対象、待つ時間は定義し直します。保険の見積依頼、自動車販売の見込み客、買い物の注文は、そのまま置き換えられません。共通して使えるのは、成果を確認し、プロセスと具体的な記録をたどって調べる手順です。
